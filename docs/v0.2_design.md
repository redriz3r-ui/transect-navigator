# Transect Navigator v0.2 — survey architecture proposal

Status: design only, 2026-10-06. No v0.2 implementation, migration, data generation,
version change or ZIP build is included in this stage.

Operating assumption confirmed by the owner: crews will return continuous GPS files
without transect labels. Field start/end markers cannot be a prerequisite. The first
usable survey workflow must therefore support analyst-reviewed assignment after import.

## 1. Baseline and compatibility boundary

The persistent folder currently identifies itself as **0.1.13-rc1**. Comparing its
runtime package with `dist/transect_navigator-0.1.12.zip` found differences only in
`__init__.py` version metadata and `metadata.txt`. The verified calculation behavior
is the 0.1.12 baseline. The complete actual QGIS 4.2.3/macOS suite was rerun during
this inspection: **283 passed, 0 failed, 0 errors, 0 skipped**.

Keep the existing single-transect entry points, defaults, output schemas and UI path
available unchanged. Add an explicit Survey workflow alongside them. A survey with
one plan and one accepted recording must reproduce existing v0.1 QA values. Do not
route legacy calls through a new association algorithm or widen existing CRS guards.
Existing packages stay readable; survey packages carry a separate schema version.

### Single-transect assumptions requiring new orchestration

- `ingest_recording` requires one planned feature and associates every input observation
  with it. Its far screen also refers to that one plan. Survey import must occur before
  choosing a plan, rather than repeatedly ingesting entire files against every line.
- `ComparisonResult` has one metric frame, one planned ID and rows corresponding to
  all ingested observations. `compare_ingested` rejects ambiguous spatial cases for
  the run. Feed it only the explicitly accepted subset for a line/bout; preserve the
  independent complete raw archive outside that subset.
- The analysis frame is local AEQD with a **5 km radius around the lexicographically
  smallest geographic plan vertex**, not around the site centre. The plan is subdivided
  into 25 m geodesic steps and limited to 2,000 working segments. Do not pass an entire
  10 × 10 km recording into one such frame.
- Constructed v0.1 raw tracks join a complete timestamp group; the construction itself
  does not split large time gaps. Survey-derived continuity tracks must split gaps
  before distance, assignment, event or coverage work. Preserve supplied track geometry
  as archival raw data and label constructed track geometry as derived.
- Summary/event adapters and event display IDs assume one transect and one run.
  Survey keys must prevent collisions across surveys, visits and reanalyses.
- `capture_analysis` requires one summary row and matching one-run layer provenance;
  its counts assume raw observations equal compared observations. Do not loosen these
  protections. A separate survey exporter must include unassigned/ambiguous raw data.
- ANALYZE selects one feature/recording; RESULTS retains only the latest successful
  snapshot. A survey needs persistent import, review, per-transect results and run history.
- Per-input limits (100,000 observations, bounded file/field sizes) remain in force.
  A many-file survey requires preflight totals and measured memory/performance limits.

## 2. Proposed architecture

```text
Planned layer snapshot + Survey_ID
                  │
                  ├── existing batch PREPARE ── survey navigation package
                  │
Many recordings ── immutable source registry ── normalized working observations
                                                   │
                                      chronology / continuity segments
                                                   │
                                      candidate transect associations
                                                   │
                                      analyst review + decision history
                                                   │
                                    accepted per-transect / per-visit subsets
                                                   │
                                      unchanged v0.1 QA calculation cores
                                                   │
                                   per-transect aggregation + survey status
                                                   │
                                      overview / drill-down / survey export
```

Proposed additive responsibilities, not files implemented in this stage:

- `survey/model.py`: typed records, stable keys, schema and state invariants.
- `survey/segmentation.py`: continuity boundaries and ordered membership, independent of UI.
- `survey/association.py`: deterministic evidence/rules, proposals and decision validation.
- `survey/aggregation.py`: visit/transect/project summaries and operational statuses.
- `integration/survey.py`: native snapshots, CRS/index adapters and existing QA services.
- `io/survey_package.py`: standard GeoPackage tables, CSV companions, source manifests,
  verified snapshots and no-overwrite publication.
- `ui/survey_panel.py`: intake, review queue, map/time-range selection and project results.

QGIS objects remain at the integration/presentation boundary. Pure records and rules
are unit-testable without QGIS. Initially process in bounded per-source/per-transect
units with explicit progress/cancellation points; do not add untested threaded access
to QGIS layer/provider objects. Persist work so closing a dialog does not discard review.

### Spatial scale and CRS

A 10 × 10 km *site* is compatible with many bounded local analyses. Preflight every
planned geometry independently against the existing metric-frame restrictions. A line
or accepted observation outside its frame becomes `REVIEW / UNSUPPORTED_EXTENT`; do
not silently split an official Transect_ID, truncate data or increase the radius.
Long individual transects need a separately validated station-preserving tiling design,
which is outside the minimum weekend scope.

Use a declared, region-appropriate projected CRS for a derived project overview and
candidate spatial index, with an explicitly recorded transformation and distortion
assessment. It is only a search/display representation. Exact QA still uses the
existing per-transect model; no metre measurements in degrees and no silent fallback
transforms. An index hit is not an assignment: QGIS index intersection queries return
bounding-box candidates, requiring subsequent geometry/evidence checks.

Different local QA frames cannot be concatenated into one layer and labelled with a
single arbitrary CRS. Keep native per-transect diagnostic layers with their frame WKT,
or explicitly transform **derived display copies** to the survey display CRS while
retaining the original numeric QA coordinates and CRS identity. Native raw snapshots
retain their own CRS and full available Z/M information.

## 3. Data model and invariants

Use a standard GeoPackage with relational attribute tables and spatial layers, plus
original files where available. No new custom container format. Original columns are
never renamed or overwritten to make room for survey fields: use mapping tables and
namespaced derived fields as in v0.1.

| Entity | Minimum fields and purpose |
| --- | --- |
| `surveys` | `Survey_ID`, name, boundary reference, declared display CRS WKT, plan snapshot digest, created UTC, schema version |
| `planned_transects` | Composite key `(Survey_ID, Transect_ID)`, original feature key, geometry/CRS, direction, plan revision, native attribute mapping, measured-length/model status |
| `surveyors` | `(Survey_ID, Surveyor_ID)`, display name or code; identity is user-supplied, never inferred from spatial proximity |
| `sources` | `Source_ID`, `Survey_ID`, `Source_File`, original path/name, file SHA-256 or loaded-layer snapshot digest, source kind, import UTC, original CRS/schema, archived reference, import status |
| `recordings` | `Recording_ID`, `Source_ID`, sublayer/device/track identity, nullable `Surveyor_ID`, field/timezone/accuracy mappings, structural segment identities; one file may contain several recordings |
| `raw_observation_index` | Globally unique `Observation_ID`, `Recording_ID`, original feature/row/trackpoint key and source order, raw table/geometry reference; every retained observation is represented |
| Native raw layers | Per source/sublayer/schema/CRS observation and recorded-track snapshots with original fields/geometry; exact original timestamps and all available GNSS fields remain here |
| `normalized_observations` | `Observation_ID`, working lon/lat, original timestamp plus nullable UTC timestamp, time/position validity, raw accuracy/HDOP/PDOP/satellites/fix/elevation references; units/meaning only when explicitly declared |
| `continuity_segments` + membership | `Segment_ID`, recording/structural group, ordered Observation_IDs, start/end time, order basis, boundary reasons, missing-time/gap flags; no raw geometry replacement |
| `association_candidates` | Run, segment or observation range, candidate Transect_ID, distances, station sequence, heading/progress evidence, uncertainty evidence, alternatives, rejection/review reasons, rule/parameter version |
| `assignment_membership` | `(Run_ID, Observation_ID)`, nullable Transect_ID/Visit_ID, `Assignment_Status`, `Activity_Role`, `Confidence_Class`, `Decision_ID`; at most one accepted transect per observation per run |
| `assignment_decisions` | Decision/revision IDs, superseded decision, exact member IDs, proposed/accepted/ambiguous/unassigned action, candidate list, reviewer, UTC, reason, plan/run/parameter digests |
| `visits` | `Visit_ID`, Transect_ID, Surveyor_ID, recording/segment links, temporal bounds, `Traversal_Direction` = FORWARD/REVERSE/MIXED/UNKNOWN, review status; separate repeated passes remain distinct |
| QA observations/events | `Run_ID`, Survey_ID, Transect_ID, Visit_ID, Observation_ID links, existing deviation/station/progress/time/GNSS fields; events have globally unique keys and retained display IDs |
| `transect_summary`, `survey_summary` | Lengths with measurement model, counts/denominators, QA descriptions, coverage, operational status/basis, unresolved/error counts, run/parameter revision |
| `analysis_runs` | Run_ID, input/plan/review digests, plugin/QGIS/PROJ context, parameters, algorithm/schema versions, started/completed UTC, processing status and failure ledger |

A file hash alone is not an observation ID. Namespace the original row/trackpoint key
by stable source content identity and recording/sublayer identity; include Survey_ID
where needed. Store the construction/version so IDs are reproducible. Never use a
mutable QGIS layer ID or an output GeoPackage FID as the portable identity.

Repeated import of the same source bytes/recording must be detected and offered as
reuse of the existing import, not silently doubled. Renaming a file must not duplicate
it. Overlapping recordings from different files are only **suspected** duplicates;
retain both originals and require a logged include/exclude decision. Equal positions
with different times are legitimate observations, including stationary runs.

A source with unknown surveyor remains explicitly unknown. One recording is not
assumed to represent one person if field metadata contradicts that. No person’s points
are joined with another person’s, even when times and locations overlap.

For each run, every raw observation has exactly one disposition: ASSIGNED, AMBIGUOUS
or UNASSIGNED. Activity is a separate field: SURVEY, TRANSITION or UNKNOWN. Thus a
transition can be UNASSIGNED/TRANSITION without pretending it belongs to a transect.
Invalid geometry/time has its own validation state; raw bytes/attributes still remain
available. A rejected file is listed explicitly and cannot masquerade as a successful
empty import. A partially processed survey is visibly partial.

`Confidence_Class` describes evidence, e.g. REVIEWER_CONFIRMED, RULE_SUPPORTED,
MULTIPLE_PLAUSIBLE or INSUFFICIENT_EVIDENCE. It is **not a calibrated probability**.
A manual confirmation records human judgment, not proof that the GPS is accurate.
Numeric evidence remains available rather than being hidden behind a confidence label.

## 4. Batch PREPARE

1. Register Survey_ID and freeze the planned layer snapshot/revision.
2. Validate nonblank unique Transect_IDs across the selected survey scope and validate
   every geometry/CRS. Show unsupported plans before navigation export or analysis.
3. Reuse existing multi-feature waypoint generation. Preserve official line direction,
   existing human-readable Waypoint_IDs and per-transect Sequence. Survey_ID provides
   a separate namespace rather than changing legacy waypoint IDs.
4. Export one survey navigation package containing every included plan and waypoint,
   survey/plan metadata and optional standard GeoJSON/GPX/CSV companions. Existing
   per-feature attributes preserve any intended team allocation; allocation does not
   prove who actually walked the line.
5. Keep per-transect direction/spacing overrides optional and out of the first increment.
   Crews may walk either direction regardless of waypoint order. Do not reverse source
   geometry to match a walk. Navigation with reversed waypoint order remains the
   existing explicit PREPARE operation.

Navigation exports are already batch capable today. The new work is survey identity,
manifest/status/preflight and later assignment support, not a replacement waypoint engine.

## 5. Batch ANALYZE and conservative association

### Intake and segmentation

Import all files independently before any transect association. Store raw sources once,
then derive working observations. Retain supplied GPX segment boundaries. Default to
no cross-file join, even for the same surveyor; future explicit continuity links need
review and must not erase the original boundary.

Partition only on defensible boundaries: source/recording/surveyor/structural segment,
validated time discontinuities, large spatial jumps, impossible movement and reviewed
visit boundaries. Time and distance gap parameters are recorded operational settings,
not wildlife standards. A suspected jump is a boundary/notice, not deleted GPS data.
Heading is unusable during a stop or movements below the positional-noise scale.

Reuse the strict v0.1 chronology policy within the chosen structural group: incomplete,
invalid or duplicate times do not gain an invented order. Such a group can be reviewed
spatially and accepted for point QA, but cannot claim time-based events or supported
track/coverage until ordering is defensible. Recorded vertex order is retained as
structure, not fabricated timestamps. Any future partial valid-time recovery requires
explicit boundary tests; it is not a weekend shortcut.

### Candidate generation and evidence

Never assign an observation simply to its nearest line. For each continuity segment,
retain all spatially plausible candidates and evaluate them over runs of observations.
Use a spatial index to limit candidates, followed by exact per-line distance/station
checks. The search corridor is separate from deviation-class and completion settings.

Evidence must include:

- a sustained sequence plausibly following a candidate, rather than one nearby fix;
- progression along that line and movement alignment in either traversal direction;
- time/spatial continuity and consistency with neighbouring observations in the same
  source segment;
- alternative candidates and how long ambiguity persists;
- proximity to starts/ends and transitions as supporting evidence, never a requirement
  that would eliminate partially completed lines;
- source GNSS uncertainty where its units/meaning are known, and an explicit unknown
  state otherwise. HDOP/PDOP are not metre radii; missing accuracy is not zero error.

Use transparent, versioned rule gates and evidence summaries initially, not an opaque
trained classifier or an uncalibrated percentage score. Candidate ranking can order
review suggestions, but ties or insufficient separation remain unresolved. Parameters
such as minimum supported run, heading tolerance and candidate margin must be recorded
and tested; no universal field-valid defaults are claimed by this design.

For a concrete first proposal rule, calculate candidate station increments and
distance summaries over each uninterrupted window. Record station span, net progress,
`abs(sum(delta_station)) / sum(abs(delta_station))` when the denominator is meaningful,
and movement-versus-local-tangent alignment modulo 180 degrees. Both forward and
reverse runs can satisfy these checks. Stops have unknown heading rather than zero
misalignment. A proposal requires sustained support and progress/alignment as well as
spatial plausibility; every competitor is tested against the same gates. Contradictory
direction, unresolved competing support or insufficient motion returns review, not a
nearest-distance winner. Turnarounds create reviewed subruns; they are not deleted to
improve the ratio. These features prioritize review only in the first release.

Once a visit is confirmed, ordinary lateral drift and sustained deviation must remain
in that visit’s QA observations. **Do not trim to the QA corridor or switch to a closer
adjacent line**, which would make deviation statistics artificially good. The reviewer
must see candidate-envelope exits and all excluded/uncertain points. A large unresolvable
excursion may remain ambiguous, but its omission is counted and disclosed; statistics
then describe only the accepted subset, not the whole recording.

### Review and final decisions

For the first usable v0.2, rules produce proposals; an analyst accepts transect visits
on the map and time axis. The system records exact observation membership, not just an
editable start/end display time. The reviewer can split a proposed run, select a
transect, mark transition, or leave it ambiguous/unassigned. Review can be saved and
resumed, and changing a decision creates a new revision and invalidates affected QA.

Multiple plausible transects remain AMBIGUOUS even if one is marginally closer. With
coincident lines, or a transition that follows another planned line, geometry and time
alone cannot establish the surveyor’s intention. If no independent evidence exists,
leave the case unresolved. Survey completion must not depend on inventing that intent.

Only accepted membership enters per-transect QA. Do not duplicate an ambiguous fix
into two official summaries. Candidate diagnostics may show both possibilities, with
a clear provisional label and exclusion from accepted totals.

### Edge-case policy

| Situation | Required treatment |
| --- | --- |
| Transition between transects | Separate role/membership; retain points, exclude from transect QA unless reviewed as a real visit |
| Nearby/overlapping lines | Retain competing candidates; no ID-order, nearest-distance or roster tie-break; unresolved lines get REVIEW |
| Reverse traversal | Keep the official planned geometry; station decreases in time, sign remains left/right of the official direction; record reverse visit |
| Mid-line turnaround/revisit | Preserve backtracking and repeated observations; separate reviewed bouts when appropriate; union station support, do not add percentages |
| Partial line | Accept a valid partial visit without requiring endpoints; report observed intervals and remaining gaps |
| No observations | NOT_SURVEYED means no accepted evidence in the imported dataset, not proof it was skipped; a reported skip requires a separate reason/log |
| GPS gap | Break continuity, track length, events and coverage; no invented connector across the gap |
| Missing/duplicate timestamps | Preserve observations, flag chronology, allow spatial QA only when association is confirmed; time metrics may be NULL |
| Multiple files/surveyors | Separate namespaces and chronology; explicit provenance; never join merely by time or nearest location |
| Multiple visits to one line | Per-visit results plus line aggregate; no duplicate coverage credit; show sampling/visit counts |
| Invalid/unsupported plan or failed analysis | REVIEW with processing error, not NOT_SURVEYED or a silent omission |

## 6. QA aggregation, status and project outputs

The original QA core continues to receive one directed official plan. An accepted
subset is a **derived analysis view**, not a replacement raw source. Split its analysis
group at every gap, transition, ambiguous/unassigned interval or excluded duplicate.
Simply dropping excluded points and retaining the old group would create false joins.
Never bridge those boundaries even when the remaining adjacent times are close.

For each line, aggregate all accepted visits while preserving group boundaries. The
existing statistics core can union supported station intervals across independent
groups. Recompute means/RMSE/percentiles from accepted observations (or equivalent
sufficient statistics where valid); do not average per-visit means or percentiles.
Report observation-weighted results and per-visit counts, because repeated passes,
stops and uneven sampling can dominate the aggregate. GNSS summaries remain separate.

Keep these quantities distinct:

- **Accepted track length:** sum of measured within-bout edges, no cross-gap,
  cross-person, cross-file or transition joins. This is not v0.1’s full raw-track length.
- **Observed progress support:** union of defensibly ordered, gap-limited station
  intervals irrespective of QA class. It describes observation support, not compliance.
- **QA corridor coverage:** existing v0.1 support rule additionally requiring both
  adjacent deviations to be within threshold C. This remains user-configurable.

For consistent project aggregation, precompute the v0.1 local-model planned length
`L_t` for every analyzable planned transect, including those without recordings. Store
PREPARE’s ellipsoidal length separately with its measurement model; do not mix its
metres with local-model station intervals silently. Unsupported model lengths remain
unknown and make an exact whole-survey metric unavailable; show known subtotals and
missing-plan counts instead of shrinking the denominator without disclosure.

For all valid modeled plans, define `C_t` as the union length of accepted QA-support
intervals on that plan. Report `100 * sum(C_t) / sum(L_t)`, not the mean of line
percentages. Repeated visits to a line cannot exceed its length. Distinct official
Transect_IDs remain separate survey obligations even if their geometries overlap;
one ambiguous visit is not counted for both. This is a length-weighted transect
support metric, not area coverage over the 10 × 10 km site.

Unobserved/unresolved portions add no confirmed support. Report **confirmed coverage
as a lower bound from imported evidence**, alongside unknown-coverage and review
counts. A chronology-unknown line retains NULL evaluated coverage rather than being
mislabelled a measured zero. If any such lines exist, mark whole-survey evaluated
coverage incomplete; distinguish the known-support lower bound from a complete result.

### Operational statuses

Status is separate from deviation classes and GNSS quality. Proposed deterministic
precedence for the displayed project map:

1. `REVIEW`: unresolved relevant assignment, unsupported geometry, failed processing,
   unknown chronology needed for completion, or an unresolved status decision.
2. `NOT_SURVEYED`: no accepted visit and no candidate evidence needing review; more
   precisely, not observed in current imported data. Optional disposition records a
   human-reported skip without conflating it with no returned file.
3. `COMPLETE`: accepted evidence satisfies a project-selected operational completion
   policy or an explicit reviewer disposition with its reason recorded.
4. `INCOMPLETE`: accepted observations exist but completion is unsupported under that policy.

Store Suggested_Status, Final_Status, Status_Basis, Reviewer and Completion_Policy_ID.
A new project must explicitly choose a completion policy; do not introduce a hidden
scientific default. Example test policy: full gap-limited observed-progress support
plus both ends, with only numerical tolerance. It is independent of deviation pass/fail.
A line can be operationally complete and still show a large deviation event.

| Survey output | Definition |
| --- | --- |
| Planned count | All registered planned features in the frozen survey scope; show valid/unsupported counts |
| Complete/incomplete/review/not-surveyed counts | Mutually exclusive final operational statuses; totals reconcile to planned count |
| Skipped count | Separate explicitly reported disposition, never inferred from absent GPS |
| Total planned distance | Sum of consistent modeled plan lengths, with completeness/model declaration; also retain navigation geodesic total |
| Total analyzed distance | Explicitly labelled unique accepted observed-progress support; also report accepted track length separately |
| Project QA coverage | Confirmed length-weighted support under threshold C, with evaluability/unknown flags |
| Per-transect QA | Lengths, visit/person/source counts, accepted/unresolved observations, deviation and GNSS descriptions, events, both support metrics, status and reasons |
| Per-surveyor/source provenance | Source registry, import/duplicate/error state, time range, original CRS/mappings, accepted/transit/ambiguous/unassigned counts, visit links |
| Project map status layer | Copy of every planned geometry with status, review reason and support values; no source styling/editing |

Processing state (DRAFT, PARTIAL, FINISHED_WITH_REVIEW, FINISHED) is separate from
transect operational status. A successfully exported package may correctly contain
unresolved cases; its summary must disclose them prominently.

## 7. UI and package changes

Keep the v0.1 single-transect workflow accessible. Add a Survey workspace:

1. **Survey setup / PREPARE:** Survey_ID, planned layer/ID, scope, geometry/extent
   validation, many-line waypoint preview and survey navigation export.
2. **Recordings:** add many files, map surveyor and optional fields per recording,
   show time ranges, counts, CRS, duplicate/import warnings and preserved-source location.
3. **Association review:** map + time/range list, candidate lines and evidence,
   direction, gap markers, all raw points, confirm/split/transition/unassigned actions.
   Do not preselect a marginal candidate as if it were confirmed. Save review revisions.
4. **Analyze accepted visits:** progress per line, failure ledger, explicit partial-run
   state, unchanged QA settings and per-transect drill-down.
5. **Survey RESULTS:** status map/table, count reconciliation, coverage with unknown
   flags, per-surveyor/source filters, REVIEW queue, and existing line-level profiles.
6. **Export survey snapshot:** standard GeoPackage/CSV and README, fixed analysis and
   assignment revisions, source references/copies and all unresolved data retained.

Use one QGIS survey group with Planned/Status, Navigation, Raw by Source, Assignment
Review, and Derived QA subgroups. Avoid creating a separate visible layer for every
person × file × line when a filtered overview suffices. Raw native layers remain
available independently of derived merged display layers.

The survey package uses a new schema with tables described above, per-source native
raw layers, a single derived working-observation view, accepted QA, event/coverage
outputs and review history. Store any original supplied files with checksums in a
standard `sources/` directory when creating a self-contained survey archive. Relative
paths plus a manifest must survive moving the whole package. Loaded in-memory sources
are archived as explicit snapshots rather than claiming original device bytes exist.

Preserve existing no-overwrite and verify-before-publication behavior. Persisted review
work can use explicit revisions/new package names initially; concurrent multi-user
editing or cloud synchronization is outside v0.2’s minimum scope. Multiple *field*
surveyors do not require multiple simultaneous desktop database writers.

## 8. Known-answer synthetic v0.2 survey (design, not generated)

Use a declared 10 × 10 km site, three surveyors S01/S02/S03 and twelve 1,000 m planned
transects. Spread lines across four blocks (roughly southwest, central, northeast and
northwest). Use geographic input and a regional projected companion to test mixed CRS.
The test-only generator should use an independent ellipsoidal reference construction
and frozen station/offset truth, not production assignment/QA output as its oracle.
Reference-generation tools are development-only; no new plugin dependency is required.

For clarity, schematic metre-grid placements are: T01/T02/T03 at y=500/700/900,
x=500…1500; T04/T05/T06 near x=4000…5000, y=3000/3300/3312; T07/T08/T09 near
x=7500…8500, y=6500/6800/7100; T10/T11/T12 near x=500…1500, y=9000/9300/9300.
T11 and T12 coincide exactly. These are layout sketches, not an assertion that 1,000
projected grid metres equal 1,000 ellipsoidal metres: freeze independent 1,000 m
geodesic endpoints and coordinate-reference expectations when authoring the fixture.

Normal survey sampling is 10 m progress every 10 seconds (~1 m/s). Small lateral
jitter is retained: except for T02 and T08, use offset `(-1)^k` metres at station
`10*k`, with offset zero at official endpoints 0 and 1,000 m. T02 uses +1 m for
all interior fixes and zero at both endpoints; traversal is reversed. The repeated
T07 visit uses the same station/offset pairs at distinct times in reverse order.
For T04, set time at station 500 to start +900 seconds (after station 400 at +400),
then resume 10-second sampling; keep it in one structural segment so the continuity
logic must detect the 500-second/100-m gap. Transition legs have 15 interior fixes each and realistic elapsed
time based on their travel distance; their endpoint fixes belong to neighbouring
visits. All sources are continuous and contain **no Transect_ID labels**. The intended
truth and deterministic reviewer decisions are separate test fixtures.

## 9. Implementation stages and acceptance gates

1. **Freeze compatibility:** preserve the verified artifact and regression suite;
   establish an isolated v0.2 branch/copy before code work (the persistent folder has
   no Git metadata today). Add single-plan survey-adapter equivalence tests.
2. **Survey setup and intake:** schema/identity, plan preflight, multi-file source
   registry, raw preservation, duplicate import checks and resumable state. Reuse batch
   PREPARE. Gate: exact source counts, hashes, native attributes/geometry and namespaces.
3. **Reviewed visit workflow:** gap-safe segments, map/time/member selection, explicit
   assignment/transition/unresolved states and decision revisions. Gate: all raw points
   accounted for; no automatic joins or forced ambiguous assignments.
4. **Batch QA and overview:** accepted visits through unchanged QA cores, line interval
   unions, statuses/unknown flags, source/person views and survey export. Gate: original
   283 tests plus the reviewed synthetic oracle and real-QGIS multi-file smoke tests.
5. **Conservative proposal engine:** spatial candidates + sustained heading/progress/
   continuity evidence, review suggestions and ambiguity diagnostics. Gate: unlabelled
   proposal tests, adversarial nearby/overlap cases, no deviation-corridor censoring.
6. **Scale and field validation:** real returned recordings, memory/time benchmarks,
   failure recovery, cross-platform tests and only then broader automation/long-line scope.

Each stage must be independently usable/testable. Existing single-transect behavior
is not replaced at any intermediate point. No deadline is a reason to waive source
integrity, review history, the 5 km guard, or numerical regression checks.

## 10. Risks and minimum weekend scope

The principal risk is **unidentifiable intent in continuous unlabeled GPS data**.
Parallel/coincident paths and on-line transitions can be indistinguishable from real
transect work. More scoring cannot manufacture missing evidence. The operational cost
is analyst review, and some cases must remain unresolved after review.

Other risks: huge candidate/observation combinations, repeated-pass sampling bias,
clock/timezone errors, duplicate files, different native schemas/CRSs, mixed uncertainty
units, suppressed large deviations through selective assignment, gap bridging, invalid
plans exceeding the local frame, and memory held by many snapshots. Keep these visible
through limits, provenance, explicit nulls, deterministic revisions and per-unit errors.
An incomplete import or unsupported line must never inflate the project completion rate.

**Smallest defensible v0.2 deliverable for this weekend:** existing batch PREPARE plus
multi-file immutable intake, manual analyst-confirmed map/time-range visits, explicit
transition/ambiguous/unassigned states, gap-safe per-transect QA, per-line/source summaries,
a simple status map and verified survey export. Automatic proposals are optional only
after their tests pass; autonomous automatic assignment is not a weekend dependency.
Do not include route optimization, mobile navigation, real-time sync, probabilistic
map matching, long-transect tiling, protocol certification or weighted error correction.

Because crews cannot label transects, an analyst must budget time to inspect each
continuous recording after return. If the reviewed workflow cannot be implemented
and validated in time, use the already verified v0.1 for batch navigation, archive
original returned files unchanged, and analyze carefully saved, explicitly documented
per-transect **copies** in QGIS.
A mere point selection is insufficient: v0.1 ingestion reads the input layer, so create
a distinct subset layer and retain the original file plus exact member-ID/time-range
mapping. That fallback is manual and has no trustworthy automated survey completion
dashboard. It is preferable to publishing confident but unverified assignments.
